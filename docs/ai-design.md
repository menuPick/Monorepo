# AI 설계: 메뉴 추천 · 위험 메뉴 판별

> 기준일: 2026-11-10 · 코드: `ai/` (Python, FastAPI)

## 구조

```
Flutter 앱 ──▶ Java API 서버 (server/, :18080) ──▶ Python AI 서버 (ai/, :18090)
                    │                                   ├ 기본: 그래프 엔진 (O(N+E), 0.1ms 미만)
                    │                                   └ AI_ENGINE=llm: Ollama(:11434) → 실패 시 그래프 엔진
                    └ AI 서버가 없거나 실패하면 Java 규칙 엔진
```

- 앱은 AI 서버를 직접 부르지 않습니다. Java 서버만 부르며 기존 API 계약은 그대로입니다.
- AI 서버는 저장소를 갖지 않습니다. 결과 저장은 Java 서버가 합니다.
- Java 서버 설정: `AI_BASE_URL`(비우면 AI 끔), `AI_SERVICE_TOKEN`(공유 토큰), `AI_TIMEOUT`(기본 90s).
- AI 서버 설정: `AI_ENGINE`(`graph` 기본 / `llm`), `AI_SERVICE_TOKEN`, `AI_PORT`(기본 18090).
  LLM을 쓸 때만: `OLLAMA_URL`(기본 `http://127.0.0.1:11434`), `OLLAMA_MODEL`(기본 `qwen2.5:7b`), `OLLAMA_TIMEOUT_SECONDS`(기본 75), `OLLAMA_NUM_GPU`(기본 0 = CPU).

## 그래프 엔진 (기본, `ai/app/graph_engine.py`)

LLM은 답 하나에 10~15초가 걸려(CPU 추론) 효율을 위해 2026-11-10에 키워드 검색 + 그래프 알고리즘으로 바꿨습니다.

| 기능 | 알고리즘 | 시간 복잡도 | 측정 |
|---|---|---|---|
| 키워드 찾기 | 키워드마다 입력에서 부분 문자열 검색 | **O(N), N = K×L** | — |
| 메뉴 추천 | 키워드 찾기 + 메뉴 지식 그래프 다중 시작점 BFS | O(N + V + E) | 약 0.06ms |
| 위험 판별 | 위험 키워드 찾기 | O(N) | 약 0.009ms (L=2000일 때 0.09ms) |

(K = 키워드 수: 위험 49개·추천 표현 95개, L = 입력 길이 ≤ 2000, V = 그래프 노드 38, E = 간선 87. LLM 대비 약 25만 배 빠름.)

- **왜 K×L 방식인가:** 처음엔 Aho-Corasick(O(L + 일치 수))을 썼지만, 파이썬으로 짠 자동자는 한 글자씩 파이썬 코드로 돌고 `in` 검색은 C로 돌아서, 이 크기에서는 K×L 검색이 2~6배 빨랐습니다(L=2000 위험 판별: 507µs → 95µs). 키워드 수와 입력 길이가 작고 상한이 정해져 있어 K×L 방식을 씁니다.
- **그래프:** 노드는 메뉴 23개와 특징 15개(매운, 국물, 따뜻한, 채소, 비빔, 면, 고기 …). 간선은 메뉴–특징, 비슷한 메뉴–메뉴(무방향 인접 리스트). 구축은 서버 시작 시 1회 O(V+E).
- **추천:** 입력에서 특징·메뉴 표현을 찾아 시작 노드로 삼고, 시작 노드 전체에서 BFS를 한 번 돌려 거리를 구합니다(각 노드·간선 1회 방문). 점수는 ① 시작 노드와 바로 이웃한 수(일치한 특징 수, 메뉴 이름을 직접 말하면 +2) ② BFS 거리 ③ 메뉴 목록 순서로 정합니다. 단서가 없으면 비빔밥.
- **위험 판별:** 위험 키워드를 모두 찾아, 걸린 규칙 중 가장 높은 점수를 씁니다.
- 한 글자 표현(국·면·밥·탕)은 "먹으면"·"설탕" 같은 낱말과 겹쳐 오탐이 나므로 쓰지 않습니다.
- 메뉴·특징·키워드를 늘리려면 `MENUS`, `ATTRIBUTES`, `SIMILAR`, `RISK_RULES` 표만 고치면 됩니다.
- 테스트: `ai/tests/test_graph_engine.py`(겹치는 키워드 검색, 최대 입력 검색 속도, BFS 거리·전 노드 1회 방문, 그래프 크기, 4000회 2초 이내).

## 기능 1: 메뉴 추천 (`POST /v1/recommend`)

- 입력: `menuName`, `reason` (사용자가 쓴 그대로).
- 출력: `recommendedMenu`, `confidence`(0~1), `reasons`(1~3개), `engine`.
- 사용 시점: 사용자가 **원하는 메뉴를 적지 않았을 때만**(빈 칸·"메뉴명 미입력"·"아무거나" 등, `WantedMenu`) 동기 호출합니다. 원하는 메뉴를 적었으면 그 메뉴를 그대로 저장하고 AI는 위험 판별만 합니다(2026-11-10: 비빔밥을 적었는데 AI가 김치찌개로 바꾸던 문제 수정). 실패하면 Java 규칙 엔진 결과를 저장합니다.

## 기능 2: 위험 메뉴 판별 (`POST /v1/assess`)

- 입력: `menuName`, `reason`, `recommendedMenu`.
- 출력: `riskScore`(0~1), `riskLevel`(≥0.7 `high`, ≥0.4 `medium`, 그 외 `low`), `flags`, `reasons`, `engine`.
- `flags`: `allergen`, `food_safety`, `not_food`, `inappropriate`, `prompt_injection`, `unhealthy`.
- 사용 시점: 추천이 저장된 직후 백그라운드에서 실행합니다. 사용자 응답을 늦추지 않습니다.

## 관리자 승인 흐름 (AGENTS.md 원칙)

1. 추천 저장 → Java 서버가 백그라운드에서 `/v1/assess` 호출.
2. 결과를 `ai_assessments` 테이블(로컬은 H2, 운영은 MySQL)에 **점수와 근거로만** 저장합니다.
3. 관리자 앱의 추천 카드에 `AI 위험 높음 · 음식 아님` 같은 표시와 근거가 나옵니다.
4. **삭제·결정 메뉴 지정은 관리자가 직접** 합니다. AI는 아무것도 지우거나 공개하거나 차단하지 않습니다.

## 중복·재시작

- 추천 1건당 판별 결과 1건(`recommendation_id` 기준 덮어쓰기). 같은 판별을 여러 번 해도 결과는 하나입니다.
- 서버가 판별 도중 재시작되면 결과가 없을 수 있습니다. 관리자가
  `POST /api/admin/recommendations/{id}/ai-assessment`로 다시 실행합니다.
- 판별 도중 추천이 삭제되면 결과를 저장하지 않습니다. 추천을 삭제하면 판별 결과도 함께 삭제됩니다.

## 안전장치

- 사용자 입력은 `<user_input>` 안에 데이터로만 넣고, 그 안의 지시는 따르지 않도록 합니다.
  지시를 바꾸려는 입력은 `prompt_injection`으로 표시합니다.
- LLM 응답은 Ollama의 JSON 스키마 출력(`format`)으로 받고, 서버에서 다시 검증·범위 보정합니다(점수 0~1, 알 수 없는 flag 제거).
- Ollama가 꺼져 있거나 모델이 없거나 타임아웃·잘못된 JSON이면 규칙 엔진으로 대체합니다.
- 로그에는 상태 코드와 오류 종류만 남기고 요청 본문·키는 남기지 않습니다.

## 사용자 화면: AI 답변 생성 중 로딩 페이지

로컬 LLM은 답을 만드는 데 10~40초가 걸리므로, 사용자 앱은 추천을 올리는 동안 전용 로딩 페이지를 보여줍니다.

- 코드: `lib/pages/ai_loading_page.dart` (`AiLoadingPage`), 호출: `lib/pages/recommendation_input_page.dart`
- 흐름: "메뉴를 올려봅시다." → **AI 답변 생성 중** 페이지 → 성공하면 결과 페이지로 교체 이동, 실패하면 입력 페이지로 돌아가 오류 메시지 표시
- 표시: 반짝이는 AI 아이콘, 진행 단계 문구(3초마다 바뀜: 메뉴 읽기 → 메뉴 고르기 → 안전 확인 → 정리), 진행 막대, `N초 경과 · 보통 10~40초 걸려요`
- 로딩 중에는 뒤로 가기를 막아 같은 추천이 두 번 올라가지 않게 합니다.
- 시간 한도: 앱 120초 > Java→AI 90초 > AI→Ollama 75초. 안쪽이 먼저 끊겨 규칙 엔진 결과로 저장되므로 앱은 보통 오류 없이 결과를 받습니다.
- 테스트: `test/ai_loading_page_test.dart`, `integration_test/recommendation_flow_test.dart`

## 모델 선택 기록

- `qwen2.5:3b`(2GB): 빠르지만(약 8초) 판단이 엉성했습니다(소주를 알레르기로 분류, 국물 요청에 비빔국수).
- `qwen2.5:7b`(4.7GB, **기본**): 이 PC CPU에서 초당 약 7토큰. 답변 품질을 위해 선택.
- 이 PC의 GPU 가속은 CPU보다 약 100배 느려 `OLLAMA_NUM_GPU=0`(CPU)을 기본으로 둡니다.

## 기능 3: 먹고 싶은 이유 자세히 쓰기 (`POST /v1/elaborate`, 2026-11-10)

- 사용자 앱 입력 화면의 "AI로 이유 자세히 쓰기" 버튼 → Java `POST /api/recommendations/reason-draft` → AI `/v1/elaborate`.
- **사용자가 쓴 말은 바꾸지 않고 뒤에 문장을 덧붙입니다.** 결과는 이유 칸에 채워지고 사용자가 고쳐 쓸 수 있습니다(저장은 제출할 때).
- 그래프 엔진: 입력에서 찾은 특징 + 메뉴의 특징으로 문장 표(`ATTRIBUTE_SENTENCES`)에서 최대 3문장 + 메뉴 문장(받침에 따라 은/는). 단서가 없으면 일반 문장 2개. O(N + V + E).
- LLM 엔진(`AI_ENGINE=llm`): 덧붙일 문장만 받아 사용자 말 뒤에 붙입니다. 실패하면 그래프 엔진.
- 위험한 메뉴(술·담배 등)는 문장에 넣지 않습니다.

## 위험한 "원하는 메뉴" 처리 (2026-11-10)

- 원하는 메뉴를 그대로 쓰기 전에 `MenuSafety`로 확인합니다: ① 서버 금지어(술·담배·주류·세제 등, AI 서버가 꺼져도 동작) ② AI 위험 판별(`not_food`·`inappropriate`·`prompt_injection` 또는 `high`).
- 위험하면 그 메뉴를 쓰지 않고 AI가 이유를 보고 고른 메뉴를 추천 메뉴로 저장합니다. 원래 입력(`menuName`)은 그대로 남고 관리자에게 AI 위험 표시가 됩니다.
- '술'은 "기술·미술·수술"과 겹치므로 낱말이 '술'로 시작할 때만 막습니다.
